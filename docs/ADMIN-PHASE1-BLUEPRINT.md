## 2. Target architecture

```
Owner ──> /admin (Supabase Auth, is_admin check) ──> Server Actions ──> Supabase (RLS)
                                                          │
                                                revalidateTag("catalog")
                                                          ▼
Customer ──> public pages (ISR, tag "catalog") ── reads ──> Supabase (anon, active rows only)
        └──> forms ──POST ids+qty──> /api/enquiry ── prices from DB ──> Apps Script (secret) ──> Sheet + email
```

- **Public reads** go through `lib/catalog.ts` (cached, tagged). If Supabase is unreachable it serves `lib/catalog.fallback.ts`, a generated snapshot of today's data.
- **Enquiry**: the browser sends ids + quantities only. The server validates (zod), prices from the DB, forwards the finished record, and stores the total *as quoted at the time*.
- **Apps Script** becomes a logger: verify secret → append row → send email. No allowlist, no prices.
- **Admin writes** are server actions that re-check `is_admin()`, validate with zod, write, then `revalidateTag`.

- `scripts/generate-seed-sql.ts` → `supabase/seed.sql`: 4 tiers, 16 options, 42 menu items, 45 party items, 2 settings, ids identical to the live site.

Executed on a real PostgreSQL 16 with stubbed Supabase `auth`/`storage` schemas (not the hosted service):

- Migration and seed apply cleanly; re-seeding is idempotent.
- Anonymous users can read active rows only and cannot write, read `audit_log`/`admins`, or call `publish_menu`.
- A logged-in **non-admin** (the open-signups scenario) cannot write anything, publish, or upload to storage.
- Admin edits are audited with old/new values; plans cannot be hard-deleted; price ≤ 0 and seasonal-with-price are rejected.
- Disabling an option hides it from anon but not from admin; offers respect their date window in IST.
- Exactly one current menu is enforced by the database; publishing swaps atomically; the current menu can't be deleted.

**Not yet tested:** hosted Supabase (Auth settings, real Storage API, PDF magic-byte check), and none of the Next.js code exists yet.

## 7. Deployment notes

- Free Supabase projects pause after inactivity and have limited backups; check current terms. For a paying client, budget for Pro or add a keep-alive plus scheduled exports. Cached pages hide an outage until the owner tries to log in.
- Env vars: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (the `sb_publishable_…` key), `SUPABASE_SERVICE_ROLE_KEY` (server only, never `NEXT_PUBLIC_`), `GAS_WEB_APP_URL` (no longer public), `GAS_SHARED_SECRET`, `TURNSTILE_SECRET_KEY`.
- Don't share zips containing `.env.local` (yours is gitignored and holds only the public Apps Script URL, but the habit matters).
