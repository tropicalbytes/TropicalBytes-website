## 1. Current architecture

```
Browser ──> Next.js 14.2.35 (App Router, React 18, TS, Tailwind) ──static config──> lib/config.ts
                │
                ├── Public pages (/, /menu, /plans, /how-it-works, /faq, /contact, /privacy-policy, /terms-of-service)
                ├── Form pages ("use client", import config directly):
                │     /plans/subscribe, /menu/request, /party-request
                └── /public/tropicalbytes-menu.pdf (static file, committed to repo)

Form submit ──POST──> Google Apps Script Web App (NEXT_PUBLIC_GAS_WEB_APP_URL, no secret)
                          ├── recomputes subscription + individual-meal totals from
                          │   google-apps-script/generated-allowlist.gs (hand-pasted from config.ts)
                          ├── TRUSTS client-supplied total for party/bulk orders (unresolved from prior audit)
                          └── writes to Google Sheet + sends email
```

No database, no auth, no server-side API routes, no middleware exist today. Deployment is Vercel (implied by `NEXT_PUBLIC_*` convention and README references) but there is no `vercel.json` — env vars are presumably set in the Vercel dashboard, so I cannot see current production values and will need you to confirm what's set there.

## 4. Compatibility findings

**A. What moves into Supabase**
All of §2's data except the PDF binary itself, which moves into Supabase Storage (the `menus` bucket) rather than the git repo. `GAS_WEB_APP_URL` stops being public (see §6/F1 below).

**B. IDs that must not change**
All 79 ids the seed generates are copied verbatim from `lib/config.ts`'s existing `slugify()` output (e.g. `weekly-veg-1`, `veg-alfredo-penne-pasta-veg`) — nothing was renumbered. These are the same ids `generated-allowlist.gs` already uses, so Apps Script needs no change to recognize them. Going forward, once rows live in the database, **the admin UI must never regenerate an id from a name** (that's the mechanism that created this fragility in the first place) — a menu item's id is assigned once, at creation, and stays fixed even if the owner renames the item.

**C. Config vs. seed differences**
Two intentional differences, both from your confirmations, not from any new decision on my part:
1. Monthly Veg prices corrected (§3).
2. `bulk_items` has 39 rows, not 45 — the 6 desserts are deliberately absent (single source in `menu_items`).
No other differences. I re-ran the generator's parity check against the current `generated-allowlist.gs` and it reports no drift on plans, menu items, or (accounting for the intentional dessert exclusion) party items.

**D. Pricing values still needing confirmation**
None outstanding — the one anomaly found in the original audit (Monthly Veg) is resolved. I found no other total that fails to match `days × meals × per-meal price` across all 16 plan options.

**E. Existing functionality that could break when connected**
| Risk | Why | Mitigation |
|---|---|---|
| Party/Bulk price trust (F1, carried over, unresolved) | `Code.gs` still stores the client-supplied `estimatedTotal` for party orders instead of recomputing it | New `/api/enquiry` route computes all three totals server-side from Supabase before calling Apps Script (§8, not yet built) |
| Three form pages are `"use client"` and import `config.ts` directly | Bundles prices into client JS; can't switch to a live data source without restructuring | Convert to server `page.tsx` (fetch) + client `*Form.tsx` (interactivity), same rendered output — no visual change |
| `Code.gs` classifies items by id prefix (`"veg-"`, `"non-veg-"`) | Fragile string matching | Not urgent to fix immediately (ids are unchanged), but should move to an explicit `category` field sent from the server route |
| Menu PDF currently served from `/public` (bundled at build time) | Switching to Storage changes the URL unless proxied | Serve a stable `/menu.pdf` route that proxies/redirects to whatever is `is_current` in Storage, so existing links/QR codes/WhatsApp shares don't break |
| CSP `connect-src` / `img-src` (`next.config.mjs`) | Currently allow only `script.google.com` and the placeholder photo hosts | Must add the Supabase project's REST/Storage host **before** any client code calls it, or requests will be silently blocked, not errored loudly |
| No fallback if Supabase is briefly unreachable | Public pages would either 500 or render empty | `lib/catalog.ts` needs a static fallback snapshot (generated from `config.ts` today) so a Supabase blip degrades to "yesterday's prices," not a broken site |
